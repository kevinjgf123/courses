## 一、为什么是 FDE

前十一册讲的都是**架构与方法**：DA / BA / AA / TA / Ontology / Agent / 知识库 / 管道处理 / 数据治理 / 主数据 / 指标。

这些册子有一个共同的隐含假设：**有一支能建平台的团队**。

但 2023 年之后，这个假设不成立了。原因有三：

1. **客户现场的数据环境是碎的**。不是「缺一个模块」，是「所有东西都要现场重写一遍」。
2. **AIP Bootcamp 把交付周期从 3–6 个月压到 5 天**。这是 Palantir 用 20 年 FDE 经验换来的，压缩的代价是把经验从人身上搬到了平台上。
3. **咨询公司交付不了**。顾问会写 PPT 不会写生产代码；开发经理会写代码但不敢进客户现场做决策。

FDE 这个岗位，就是为这三件事同时存在的。**它不是职级，是交付模型。**

## 二、Palantir 官方核实结论（本册地基）

### 三种角色（这是全册最重要的一张表）

| 角色 | 归属 | 目标 | 一句话 |
|---|---|---|---|
| **Dev**（核心产品工程师） | Core Platform / Product Development | 一种能力服务多个客户 | 建平台的人 |
| **Delta**（FDE 本体，驻场部署工程师） | Business Development | 一个客户需要多种能力 | 修路的人 |
| **Echo**（驻场部署战略师） | 客户侧，通常不是工程师 | 找到最值得修的路 | 指路的人 |

关键机制：
- **Delta 一对一配 Echo**，是刻意的张力设计：Delta 单独干会做出「技术正确但运营无关」的东西，Echo 把工作拽回真实业务问题上。
- **Echo 必须是叛逆者（heretics）**——McGrew 原话。一个觉得「现在这套挺好」的人，找不到值得派 Delta 去修的问题。
- 招聘漏斗：Palantir 估算 FDE 候选人接受率约 **1%**，全球池子几千人。
- 每个客户配 **2–4 名 FDE**，驻场周期常以年计。
- 2016 年 Palantir 的 FDE 数量**超过了传统软件工程师**。
- 每个项目 **2–6 名 FDE** 长期驻场，直接参与客户真实决策系统的构建与运行。

### 起源（2005 年，不是 AI 时代的事）

- 2005 年卖 Gotham 给 CIA / NSA / 陆军情报单位时，Karp 与 Cohen 发现：传统顾问不会写生产代码，售前工程师不敢改产品。
- 目标客户特别难伺候：需求说不清、数据不能公开分享、不同机构工作流差异极大。
- 所以决定：把员工派驻现场，带着现有产品进场，**先铺一条碎石路**；总部的产品与工程团队负责把它推广成铺好的超级高速公路。
- 「碎石路 → 超级高速公路」是 FDE 商业模式最本质的一句话：**一个客户定制 → 抽象成平台能力 → 下 5–10 个客户不用现场支持也能用**。

### 三个行动（先做什么后做什么）

1. **Enter**（进入现场）
2. **Investigate**（把真实问题挖出来）
3. **Execute**（跑生产、交付价值）

### 「ruthless commitment to truth-seeking」（官方原话）

FDE 的行为准则，翻译成中文就是：**不惜代价地逼近真相**。
- 「As a New Grad, you will be entrusted with responsibility on day 1.」
- 「You will not be handed a ticket queue.」
- 「You will not be shielded from the customer, the chaos, or the consequences.」

### AIP 时代的新增（2023 起）

| 变化 | 内容 |
|---|---|
| 交付节奏 | Bootcamp 第 3 天交付一个能跑的工作 LLM 应用；3–6 个月压到约 5 天 |
| 30–40% 时间 | 花在对话式客户发现上，每周 5–15 场对话 |
| 前置条件 | **先把 Foundry Ontology 建好，再上任何 LLM 应用** |
| 资源杠杆 | 每 200 万–500 万美元企业管道配 1 名 FDE（FDE 是管道，不是销售成本） |
| 驻场时长 | 单客户 8–16 周 |
| 规模化瓶颈 | 收入增长受制于 FDE 人力弹性，类似咨询公司受制于高级合伙人数量 |

### 行业扩散

Anthropic / OpenAI / Databricks / Cohere / Google 全都在复制。2024–2026 这几家基本用 FDE headcount 替换掉了 solution engineer headcount。

## 三、六条核心主张

1. **FDE 不是职级，是交付模型**——衡量它的指标是「客户现场生产环境的改变程度」，不是工时。
2. **Echo 与 Delta 是一对，缺一不可**——一个指路，一个修路；单独任一个都会产出错误的东西。
3. **先有 Ontology，再有 AI 应用**——AIP 时代的硬顺序，没有例外。
4. **FDE 的产出物是「可运行的生产环境」，不是 PPT**——交付即上线。
5. **个人知识必须回流成平台能力**——不回流，FDE 团队就是规模化不可解的咨询公司。
6. **FDE 与传统三 roles 的边界，靠的不是能力清单，是「交付物形态」**——这是本册要给出的判据。

## 四、FDE × 前面各册的特有处理（本册的差异化核心）

用户明确要求：**FDE 在 Ontology、Agent、知识库、管道处理、数据治理、主数据、指标、4A 架构等领域的特殊地方。**

### FDE × Ontology
- FDE 建的 Ontology 不是客户自己的 Ontology，是**平台的第 N 次实例化**——要能被下一个人复用。
- 核心考验：**这层本体是「可抽象的」还是「一次性的」**。
- 交付即意味着要在客户现场直接建对象类型、链接类型、动作类型、接口，并处理解析与写回。
- 建完必须做抽象审查：哪些是行业通用的（进平台）、哪些是客户独有的（留在客户）。

### FDE × Agent
- Agent 是 FDE 交付物里**最难验收的一类**——因为它的失败是静默的。
- FDE 的特殊责任：Agent 的出口策略、工具权限、记忆边界、遥测日志，这四件事 FDE 必须亲手配，不能交给客户 IT。
- AIP Logic 那一层（自然语言触发本体动作）本质上就是 FDE 交付的最后一段路。

### FDE × 知识库
- FDE 要在客户现场做**切片工艺**：切多大、怎么带元数据、密级怎么继承。
- 知识库是 FDE 唯一能大规模复用的交付物——因为文档切片的套路高度通用。
- 特殊风险：客户文档里的历史脏数据会被切片放大。

### FDE × 管道处理
- 管道是 FDE 最脏、最耗时、最不可复用的部分。
- 特殊处理：**FDE 必须现场写幂等、重试、批次号**，因为客户环境没有第二次机会。
- 关键判断：哪段管道能上平台（模板化），哪段必须留在客户侧（一次性）。

### FDE × 数据治理
- 治理是 FDE 的**信任基础**。没有标记与策略，Ontology 与 Agent 都不敢上线。
- 特殊处理：FDE 在客户现场做的是**最小可行治理**——先把密级和对象级策略落地，不追求一次到位。
- FDE 必须拿到「哪些数据不能进 Agent 上下文」的一票否决权。

### FDE × 主数据
- 主数据实体解析是 FDE 现场最脏的活，也是最容易做出可复用模板的活。
- 特殊处理：**解析元数据必须可逆**，否则现场合并出的错误无法撤回。
- FDE 要在客户现场把「合并/拆分」变成走审批的动作，而不是脚本直连。

### FDE × 指标
- 指标口径是 FDE 交付里最容易被绕过的一环——现场赶时间，业务方会同意临时口径。
- 特殊处理：**口径是策略不是配置**，FDE 现场签字的每一个口径都要版本化、可回放。
- FDE 必须抵抗「先跑起来再说」的诱惑。

### FDE × 4A
- FDE 不是一个架构层，是**横切所有层的一种工作方式**。
- 但 FDE 在 4A 各自的落点不同：BA 落决策链、DA 落对象与血缘、AA 落交付应用、TA 落环境与策略执行。

## 六、Approach 五阶段（第 04 页）

照用户给的图的结构：顶部阶段箭头带 + 左侧「项目实施任务分解」竖条 + 中部任务盒（**行内用 → 串，行间用 ↓**）+ 底部贯穿条。

1. **进场（Enter）** — 2–6 人配对组建、客户现场准入、脏环境摸底 → 产出：现场问题清单 · 数据环境画像
2. **诊断（Investigate）** — 决策链梳理、真实流程还原、痛点量化 → 产出：决策链路图 · 痛点优先级矩阵
3. **建模（Model）** — 先建 Ontology、再定治理与主数据 → 产出：对象与链接模型 · 密级与权限矩阵
4. **构建（Build）** — 管道、知识库、Agent、指标逐层建 → 产出：可运行的生产环境 · 场景验收记录
5. **回流与移交（Hand over）** — 抽象进平台、知识转客户、运营移交 → 产出：平台抽象提案 · 运营手册 · 陪跑计划

底部三条贯穿条：**碎石路机制** / **知识转移** / **平台回流**

## 七、FDE 与传统 roles 的边界（用户明确要求）

不是「能力清单不一样」，而是**四个维度的结构性差异**：

| 维度 | 传统咨询顾问 | 产品经理 | 开发经理 | FDE |
|---|---|---|---|---|
| 交付物形态 | PPT / 蓝图 | 需求文档 / 路线图 | 排期 / 上线报告 | **可运行的生产环境** |
| 是否写生产代码 | 不写 | 不写 | 不写（管别人写） | **写，且在现场写** |
| 失败的代价 | 客户不续约 | 需求做错 | 延期 | **客户业务停摆** |
| 停留位置 | 会议室 / 远程 | 会议室 | 内部 | **客户生产环境** |
| 与客户数据的关系 | 看 PPT | 看看板 | 看工单 | **直接读写生产数据** |
| 被追问的对象 | 项目成果 | 需求合理性 | 交付质量 | **「上线了吗，管用吗」** |

**判据一句话**：前三种角色交付的是**关于系统的论述**，FDE 交付的是**系统本身**。

## 八、FDE 的工具与工作台（用户明确要求）

这一段是本册最有实用价值的部分之一。要回答：**FDE 用什么把手艺固化成可复用的东西。**

| 类别 | 工具 / 工作台 | 干什么 | 传统对应 |
|---|---|---|---|
| 现场发现 | 对话式客户发现台 | 把每周 5–15 场对话结构化成问题台账 | 需求调研纪要 |
| 现场发现 | 决策链路画布 | 从「谁在什么会上用什么数据做什么决定」画起 | 业务流程图 |
| 现场建模 | Ontology 骨架生成器 | 从现场问题反推对象类型 / 链接类型 / 动作类型 | — |
| 现场建模 | 密级与权限矩阵工作台 | 最小可行治理的落地工具 | 安全设计文档 |
| 现场构建 | 管道骨架（含幂等模板） | 现场直接生成带批次号与重试的管道 | ETL 规范 |
| 现场构建 | 切片工艺工作台 | 文档切片 + 元数据 + 密级继承 | 知识库方案 |
| 现场构建 | Agent 装配台 | 工具白名单 / 出口策略 / 记忆边界 / 遥测 | Agent 需求 |
| 现场验收 | 上线验收台（12 项） | 逐项打勾才算交付 | UAT 报告 |
| 抽象回流 | 平台抽象提案台 | 区分「进平台的通用」与「留客户的独有」 | 复盘报告 |
| 抽象回流 | 可复用度矩阵 | 给每个交付物打「能复用到第几个客户」分 | — |
| 运营移交 | 知识转移台 | 三层移交：操作手册 / 陪跑 / 自主 | 培训 PPT |
| 通用底座 | Foundry Branching | 现场改本体可分支、可评审、可合并 | Git 分支 |

**关键判断**：传统三 roles 的工具产出的是**文档**，FDE 工作台的产出物是**可以直接上线的东西**。这是「服务业-as-软件」的核心。
