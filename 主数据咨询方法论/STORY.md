## 二、六条核心主张

1. **Palantir 没有独立的 MDM 模块——因为主数据不是一个模块，是一种建模方式。**
2. **黄金记录不再是终点，是起点。** AI 时代要的不是「一张干净的表」，是「一个可推理的实体上下文」。
3. **实体身份错了，AI 的所有输出都错。** 模型会把 J. Smith / SMITH JOHN / john.smith@… 当成三个人。
4. **合并必须可撤销。** unresolve 是主数据最被低估的能力——没有它，合并就是一次性操作。
5. **仲裁规则要版本化，被覆盖的值不能丢。** 真相是运行时算出来的，不是入库时写死的。
6. **主数据不做完，Agent 就是在猜。** 智能体需要的不是记录，是上下文——关系、层级、时效、来源、可信度。

## 三、Palantir 官方核实结论（本册新增）

### 3.1 为什么 Palantir 文档里找不到 MDM

- Ontology 官方定义：本体是组织的**运营层**，坐在数据集/虚拟表/模型之上，把它们连到真实世界的对应物。
- 本体包含**语义元素（对象、属性、链接）**与**动力元素（动作、函数、动态安全）**。
- **对象类型（object type）就是现实世界实体或事件的 schema 定义。**
  - 官方类比：对象类型 ≈ 数据集；对象 ≈ 数据集里的一行；对象集 ≈ 过滤后的一组行。
- 对象有两种产生方式：**加 backing datasource**，或**配置 action 来创建对象**。
  - 如果所有对象都通过动作创建，可以建**没有 backing datasource 的对象类型**。
- **结论**：主数据在 Palantir 的形态是「对象类型 + 对象实例 + 全局唯一主键」，不是一个独立系统。它是本体的原生组成，不是外挂。

### 3.2 对象解析（Object Resolution）——主数据最核心的机制

- 定义：**把两个或多个对象合并**（combine two or more Objects），防止同一实体产生重复对象。
- 解析元数据三件套：
  - `canonicalObjectPrimaryKey`：合并后对象的规范主键
  - `winnerObjectPrimaryKey`：内部生成的胜出主键，新的属性写入都挂在它上面
  - `otherObjectPrimaryKeys`：被合并进来的其他主键；递归合并时会被**扁平化**进这个列表
- **关键设计：unresolve（解除合并）**
  - 各对象的**独立历史被保留**
  - 对合并对象直接写的属性，在 unresolve 时可**按成分拆回**原对象
  - 目的是：解析出错时能还原
- **主数据含义**：合并不是覆盖，是「带血缘的聚合」。可退比可合更重要。

### 3.3 多数据源对象（MDO）与权限

- MDO（multi-data source object type）：把**多个输入数据源映射到同一个对象类型**的不同属性上。
  - 仅在 **Object Storage v2** 可用。
  - 输入源可以是 dataset 或 restricted view 的任意组合。
- 权限效果：
  - 数据集权限决定「能不能看到这个对象实例」
  - 属性安全策略决定「能不能看到这个属性」
  - 两个叠加 = 单元格级
- 典型场景：patient_info 带 PHI 标记 → 无标记用户看不到姓名/地址/电话/年龄；care_event_info 无标记 → 所有人可见。
- **主数据含义**：主数据的不同属性天然来自不同源、敏感度不同，必须支持「一个对象、多套权限」。

### 3.4 链接类型（Link Type）

- 定义：两个对象类型之间关系的 schema 定义。
- **天然双向**：一个 link type 有两侧，每侧独立遍历、独立显示名与 API name。建一个 `Flight ↔ Aircraft` 就够了，不需要再反向建一个。
- 可以在**同类型之间**建链接（如 `Direct Report ↔ Manager`）。
- **跨 Ontology 不支持链接**——跨域要么合并本体，要么走接口。
- 多对多时需要**给 link type 自己的 datasource**；一对一/一对多则存在对象的外键属性里。
- **主数据含义**：层级与关系是一等公民，不是 JOIN 的副产品。

### 3.5 动作类型（Action Type）——主数据如何被维护

- 定义：一组可以一次性提交的对象/属性/链接变更 + 副作用行为。
- 规则类型：Create object、Create or modify object、Delete object、Create/Delete link、Run function、Webhook、Notification、Trigger a build、Merge scenario edits、Interface rules。
- **function rule 是例外：不能与其他 ontology 规则组合。**
- Submission criteria：提交条件（参数校验、正则、权限），可配错误提示。
- 权限：动作可按用户与条件做粒度授权（分析师可发起调查，关闭调查只限主管组）。
- **主数据含义**：主数据的维护动作本身就是被治理的动作——和第九册的数据治理完全咬合。

### 3.6 写入机制（Writeback）

- 编辑写入 **writeback dataset**，不写 backing dataset。
- 结果：**原始数据与编辑数据并存**，分析里两者都能用。
- 权限分离：
  - 能看对象 ≠ 能看编辑。有 backing 权限 → 只看原始；有 writeback 权限 → 看含编辑的当前态。
- **主数据含义**：黄金记录不是覆盖源数据生成的，它是叠加在源数据上的一层「当前态投影」。原始层必须保留。
- edit-only property：对象类型已有 datasource 时，用它填单个属性。

### 3.7 接口（Interface）

- 描述一个对象类型的**形状与能力**，提供**多态**。
- 共享同一形状的对象类型可以统一建模与交互。
- **主数据含义**：「设备」可以是接口，泵/风机/压缩机是实现——主数据天然需要抽象层。

## 四、公网 MDM 理论（AI 时代的新含义）

### 4.1 Reltio / CIO 观点：黄金记录已不够

- 黄金记录告诉 Agent「这个客户存在、住哪、账号是多少」——**不够**。
- Agent 还需要知道：这个客户属于哪个家庭？持有哪些产品？受哪些合同约束？有无未结服务工单？适用什么同意权限？是否够资格升级？是否有监管限制？
- 数据都在，但**没有上下文，AI 无法可靠推理**。
- 演进路径：**黄金记录 → 可信档案（trusted profile）→ 情境系统（System of Context）**。
- 业务现实不是扁平的，是网络：客户连着家庭、账户、交易、产品、服务历史、同意记录、位置、员工。
- **关键转向**：从「数据」到「上下文」；竞争点从「谁的数据最好」变成「谁的上下文最厚」。

### 4.2 MDM 五阶段被 AI 逐段改造

| 阶段 | 传统做法 | AI 化做法 |
|---|---|---|
| 标准化 Ingest | 查表 + 正则 | 模式识别（Ltd./Limited/LTD 是同一法人形式） |
| 匹配 Match | 精确匹配规则 | 概率打分 + 学习到的相似度 |
| 合并与仲裁 Survive | 「固定来源优先」 | 按结果排序的自适应仲裁，逐属性选最优值 |
| 发布 Publish | 批量文件 | API + 事件流，按需取当前值 |
| 监控 Monitor | 抽样人工复核 | 异常检测：新增重复、漂移、断流 |

### 4.3 AI 时代 MDM 的四个新特征

1. **消费方变了**：消费方不再是月度报表，而是每秒读上千次的模型 → **陈旧度被放大**，主数据必须实时化。
2. **可解释性要求**：模型决策必须能回溯到一个有血缘的受管实体。
3. **自然语言可达**：对话式分析只有在背后的实体可信时才可信。
4. **模型继承主数据漂移**：源系统持续发散 → 黄金记录慢慢脱离运营现实 → 必须**持续管治**，不是一次性治理。

### 4.4 四个落地难点

1. **匹配与去重**：标识、语言、格式各异，精确匹配在长尾上必然失败。匹配质量决定下游一切，却最被低估。
2. **治理与归属**：主数据跨部门，没有明确 owner 时，黄金记录会变成政治产物而不是运营资产。**治理设计必须先于工具**。
3. **两速问题**：夜间批量对实时 AI 不够，需要批 + 事件双轨，且不能产生分析视图与运营视图的新分歧。
4. **B2B / B2C 双视图**：客户既是法人实体又是一组联系人；产品既是 SKU 又是套装。强行一套模型，结果是「哪条都不合适的黄金记录」。

### 4.5 监管压力

- 欧盟 AI 法案高风险义务自 **2026 年 8 月**起适用，数据准确性与治理从最佳实践变成合规要求——而实体层正是这些要求真正被执行或被打破的地方。

## 六、Approach 八阶段

1. 实体域盘点与优先级排序 → 实体域清单 + 优先级矩阵
2. 实体定义与主键策略设计 → 实体定义书 + 主键策略
3. 匹配规则与解析阈值设计 → 匹配规则集 + 阈值实验报告
4. 仲裁与生存规则设计 → 仲裁规则表 + 版本化策略
5. 层级与关系模型设计 → 层级结构图 + 链接类型清单
6. 数据质量与匹配监控设计 → 质量规则集 + 匹配率看板
7. 变更与审批流程设计 → 提案规范 + 审批流程图
8. 分发与消费治理 → 分发清单 + 消费方契约

**三条硬规则：**
- 先定主键，再谈匹配
- 先只读投影，再开放写入
- 先有撤销（unresolve）能力，再谈规模化合并
