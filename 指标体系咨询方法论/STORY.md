## 二、六条核心主张

1. **指标不是一张报表，是对象类型上的派生属性（Derived Property）。**
2. **口径即定义，定义即代码，口径必须版本化。**
3. **指标的最小单位不是「指标名」，是「指标 + 粒度 + 时间口径 + 聚合方式 + 过滤条件」五元组。**
4. **指标的失败是静默的：数字照常出来，只是和昨天说的不是一回事。**
5. **AI 时代指标从「给人看的数」变成「给 Agent 调的接口」——于是口径必须结构化到能被机器读。**
6. **指标体系的第一性问题不是「有多少指标」，是「同一个词在全公司是不是一个东西」。**

## 三、Palantir 官方核实结论（重点）

### 3.1 官方没有指标模块：指标 = Derived Properties

- **派生属性**：值在查询时从其他属性或链接对象算出，不存储。底层数据变了它自动对，不需要重跑管道、不需要维护更新逻辑。
- **三种计算方式**：
  1. 跨链接对象**聚合**（Department 暴露其关联 Employee 的平均薪资）
  2. 从单个链接对象**选取**（Employee 暴露其经理的姓名）
  3. **表达式**运算（Employee 暴露薪资 + 奖金 = 总薪酬）
- **派生属性是只读的**：不能被 action 或 function 编辑，不存储在对象存储里。
- **主键属性不能是派生属性。**

### 3.2 两种定义位置（这是全册最重要的一张对照表）

| 维度 | 本体定义（ontology-defined） | 运行时定义（runtime-defined） |
|---|---|---|
| 配置位置 | Ontology Manager | Workshop 模块 / Insight 工作簿 / Ontology SDK 请求 |
| 存储 | 本体定义 | 对象集定义 |
| 可见性 | 该对象类型的**每个**消费者 | 声明它的那个请求或模块，以及能访问它保存的对象集的用户 |
| 最大链接遍历 | **3 跳** | Workshop / Insight **1 跳**；Ontology SDK 无固定上限 |
| 表达式 | **不支持** | 支持 |
| 状态 | Beta | GA |

- 官方选用规则：**计算属于组织对该对象类型的建模方式、每个消费者都该看到 → 本体定义**；计算只属于单个应用或分析、或需要算术与日期表达式 → 运行时定义。
- 官方硬限制：
  - 一个计算属性**不能引用同一次 `withProperties` 操作中声明的另一个计算属性**，必须拆到后续操作声明
  - 链接选择与聚合**不能嵌套另一个派生属性定义**，但属性选择器可以引用已在作用域内的属性
  - 表达式只能引用**更早声明**的派生属性
  - **静态字面量在表达式中当前不支持**
  - 不能用于文本搜索或关键词过滤
  - OSv1 索引的对象类型不能出现在含派生属性的查询里
  - 不能标记为必填（非空）、不能有属性类型约束、不能有 rule set 绑定或 base formatter

### 3.3 派生属性的安全继承（与第九册数据治理的接口）

- 派生属性**从计算中用到的每一个对象继承安全性**。
- 访问检查在计算的**每个对象上执行，包括多跳遍历中的中间对象**，然后值才被组合。
- **两个用户可能对同一对象的同一派生属性看到不同的值**——每个用户的计算结果只反映其有权看到的源对象与中间对象。
- 收集成 list / set 的聚合**保留每个被收集值的安全标记**，所以列表里每个值带自己的标记。
- → **指标的口径与指标的值，必须继承同一套权限。口径写在文档里而值从本体里算，是最危险的一种分叉。**

### 3.4 聚合类型全表（10 种，1 种不可用）

| Ontology Manager 名称 | SDK 方法 | 入参类型 | 结果类型 |
|---|---|---|---|
| Count | `$count` | 不适用 | Long |
| Average | `avg` | Numeric | Double |
| Sum | `sum` | Numeric | Numeric（加宽） |
| Minimum | `min` | Numeric / string / Boolean / date / timestamp | 同源 |
| Maximum | `max` | 同上 | 同源 |
| Approximate cardinality | `approximateDistinct` | Numeric / string / Boolean / date / timestamp | Long |
| Exact cardinality | `exactDistinct` | 同上 | Long |
| Collect list | `collectList` | 除 vector 外任意 | 源类型数组 |
| Collect set | `collectSet` | 除 vector 外任意 | 源类型数组 |
| （不可用） | `approximatePercentile` | Numeric | 同源 |

- **Sum 的类型加宽规则**：short / integer → long；long → long；float → double；double → double；decimal → decimal（提高精度、降低标度）。
- 数组输入在计算前被**展平**（percentile over array 返回 integer）。
- Vector 属性不能被聚合，也不能被派生属性选取；派生属性不能产出 vector 值。
- **Collect 家族的行为陷阱**：
  - 收集值**没有保证顺序**，除非定义了 property reducer；定义了 reducer 时 Foundry 用它排序（无论是否真的应用）
  - **无值的对象被跳过** → 结果数组**永不含 null** → 「列表长度 5」不等于「5 条都有值」
  - Collect set 去重，Collect list 保留
  - Collect set **先去重再应用 limit**；**limit 默认 10，最大 100**
  - **limit 只决定返回给你多少值，不决定平台评估多少值** → 官方明确要求：依赖收集结果做过滤之前，必须先了解 collection limits
  - **先排序再截断 ≠ 先截断再排序**

### 3.5 何时必须聚合、何时可以直接选

| 链接链 | 可用操作 |
|---|---|
| 每次遍历最多到达一个对象 | 直接选属性，或聚合 |
| 任一遍历可到达多个对象 | **必须聚合** |
| 链中含多对多链接 | **必须聚合，绝不允许直接选** |
| 一对多链接且外键是数组 | **必须聚合** |

### 3.6 性能与规模

- 派生属性**查询时求值，不存储、不索引**。
- 平台能把过滤器**下推到对象索引**，减少计算前需处理的数据量。
- **按派生值过滤或排序，通常要为剩余候选对象逐个算出该值。**
- 性能取决于：过滤后剩余对象数、链接对象数量与中间结果大小、聚合类型、链接遍历跳数。
- **Workshop 中使用派生属性排序时，对象集上限 200 行**；function-backed 列支持端用户排序至 **10,000** 对象；超过 10,000 则端用户不能排序，默认排序只对每页生效。
- 官方另有专门文档指导「**该用派生属性还是该在管道里预计算**」——说明这不是二选一，而是按用途分工。

### 3.7 Aggregate Objects API

- 聚合类型：count / max / min / sum / avg / approximateDistinct
- 分组类型：exact（精确值）/ fixedWidth（固定宽度）/ ranges（区间）/ duration（时间间隔）
- **`excludedItems`：分组数超过 `maxGroupCount` 时被排除的对象数。**
  → 这是**静默丢数据**：接口成功返回、图表照常画，只是少了一批。
- v2 新增 `accuracy` 参数：
  - `REQUIRE_ACCURATE`：无法保证准确就失败（报 `AggregationAccuracyNotSupported`）
  - `ALLOW_APPROXIMATE`：允许近似结果，**这是默认值**
  - 响应回传 `accuracy: ACCURATE | APPROXIMATE`、`excludedItems`、`computeUsage`（compute-seconds）
- 多个 aggregation 顺序不影响结果；多个 groupBy 按 `groupBy` 数组顺序计算；可用 `query` 字段先筛对象再聚合。
- Null 值被忽略。`name` 可自定义返回里的指标名，省略时默认 `count` / `max_xxx` / `sum_xxx`。

### 3.8 ChatBI 路线对比（Palantir vs Text-to-SQL）

| 维度 | 传统 ChatBI（Text-to-SQL） | Palantir 路线 |
|---|---|---|
| 底层 | 数据库表 | 业务对象（本体） |
| 准确率瓶颈 | SQL 准确率、数据清洗程度 | 初期本体建模的工程量 |
| 回答能力 | 擅长「是什么」 | 复杂逻辑推理、多因素归因 |
| 场景推演 | 无 | Scenario：这批订单延迟 3 天，对现金流影响几何 |
| 执行闭环 | 只到出图 | Write-back：分析完直接下达业务指令并回写 |
| 权限位置 | SQL 层，AI 可能绕过前端碰到敏感字段 | **绑在对象级**，无「薪资」对象权限则 AI 无论如何调不出来 |

## 四、公网理论：AI 时代指标的新含义

### 4.1 语义层的工程直觉

- **原子指标 + 派生指标分层**：原子指标是最小不可再分的业务度量（订单金额、商品数量）；派生指标由运算规则组合（客单价 = 订单金额 / 订单数）。
- 分层的三个收益：避免重复计算、变更影响可控（改原子指标自动同步所有派生）、查询性能可优化。
- **中等规模企业的语义层通常包含 300–500 个核心指标定义。**
- **语义层不是数据字典，而是指标计算图谱**：毛利率明确写为 (收入 − 成本) / 收入，并关联到具体字段与计算规则。
- 定义要**以代码/结构化配置形式管理**（如 YAML），而不是写在 Wiki 里。

### 4.2 指标三层与复合指标

- 原子指标 → 派生指标（比率、均值、差值）→ **复合指标**（达成率、同比环比、加权综合评分、结构占比）。
- 复合指标最容易失控：它把多个口径串在一起，一处错、全链路错，且往往没有单一责任人。

### 4.3 AI 时代的三次变化

| 变化 | 说明 |
|---|---|
| **消费者变了** | 消费者从人变成 Agent。人会问「你说的是什么意思」，Agent 不会——它只会算 |
| **容错变了** | 人看到荒谬的数字会怀疑，Agent 会把它当事实写进报告。**指标错误第一次获得了行动能力** |
| **生命周期变了** | 传统 BI 指标上线即固化；AI 时代指标要能被机器发现、解析、组合、调用，因此必须结构化到能被读懂 |

### 4.4 五类典型口径失效

1. **同名不同义**：三个部门都叫「销售额」，口径分别是订单额 / 到账额 / 签约额
2. **同义不同名**：「营收」「收入」「销售额」三套报表三个名字，一个口径
3. **粒度错配**：把日粒度明细直接求和当月度量；把订单粒度的均价按数量加权
4. **时间口径错配**：自然月 vs 财年 vs 滚动 30 天；时区；截止时点（是否含当日未结算）
5. **聚合方式错配**：去重计数当计数；用平均值算总额；null 当 0 参与运算
