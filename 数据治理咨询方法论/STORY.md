## 二、核心主张

1. **治理不再是管数据，而是管「谁能用、用来干什么、出了事谁担责」。** 数据保护的对象是数据；数据治理的对象是数据保护与使用的全过程，从接入到访问到删除。
2. **标记（Marking）是治理的最小可执行单位。** 权限可以撤，标记撤不掉——标记一旦创建就不能删除、不能移到别的类别。所以标记的划分必须在第一天想清楚。
3. **策略必须是数据，不是配置。** 标记、组织、分类是主动式不可变元数据，血缘与安全引擎协同工作，能说清「谁访问了什么、为什么」。
4. **治理的失败是静默的。** 一个标记漏打，会在几个月后以「数据泄露」的形式出现，而不是以「治理没做好」的形式。所以必须有降级审批与双签。
5. **AI 时代治理对象多了一层。** 除了数据本体，还有智能体记忆、工具调用、日志本身。日志的密级与数据的密级要用同一套标记管。
6. **治理必须可退。** 策略改错要能退回上一版，且要能回答「这次放宽了谁的权限」。

## 三、Palantir 官方核实结论（本册引用依据）

### 数据保护与数据治理的官方定义
> "Data protection refers to the range of technical and organizational means available to ensure that the processing of personal data is at all times limited to that which is necessary and proportional to achieve a legitimate processing outcome."
> "Data governance refers to the management of enterprise data across the entire lifecycle of processing, **from ingestion to access to deletion**."

关键区分：**数据保护 = 手段（必要且相称）**；**数据治理 = 全生命周期管理（接入→访问→删除）**。

### FIPPs 公平信息实践原则（OECD 指南为基础，八项）
1. 采集限制（Collection Limitation）
2. 数据质量（Data Quality）
3. 目的规范（Purpose Specification）
4. 使用限制（Use Limitation）
5. 安全保障（Security Safeguards）
6. 公开性（Openness）
7. 个人参与（Individual Participation）
8. 问责（Accountability）

贯穿其中的主题：**数据最小化**——只为明确且授权的目的采集与使用。

### Marking（标记）机制
- **Marking category（标记类别）**：类别一旦创建不能删除
- **Category visibility**：`Visible`（默认，名称与描述本身通常不敏感）/ `Hidden`（类别存在本身即敏感信息，只对显式授权的 Category Viewer 可见）
- 可见性按**类别**分配，不能逐个标记分配
- **Marking 的四种权限，彼此独立、不会自动带来成员资格**：
  | 权限 | 含义 |
  |---|---|
  | Manage permissions | 授予权限、管理成员与元数据 |
  | Apply marking | 只能打标记，**不含成员资格** |
  | Remove marking | 移除标记（还必须具备 Apply marking 能力） |
  | Members | 只有成员才能看到被该标记保护的资源 |
- 官方特别提醒：一个人可以有 Apply marking + Manage permissions 而**不是** Member——他能给数据打标记、管标记，但看不到被标记的数据
- **Marking 一旦创建不能删除，也不能移到别的类别**
- 打标记是敏感操作，会影响下游用户
- Marking 全局授予用户，但有标记 ≠ 能看全部内容，仍需通过角色获得权限
- **标记可按组织隔离**：一个标记类别可限制到单一组织，绝不外泄

### 四种访问控制的融合
| 控制 | 逻辑 | Foundry 中的角色 |
|---|---|---|
| RBAC 基于角色 | 属于某组即可访问 | 只用于管理功能权限（如能否编辑），**不用于数据可见性** |
| MAC 强制访问（Marking） | 数据带标记，用户须有对应标记 | 支持多维标签组合（PII + Secret + Operations） |
| ABAC 基于属性 | 按属性动态判定 | Restricted Views 与 granular policies，行级动态计算 |
| **PBAC 基于用途** | 有权限还要声明理由 | **Checkpoints 检查点机制**，传统系统普遍缺失 |

PBAC 的两种模式：
- **被动模式**：记录理由后立即放行，用于事后审计（威慑）
- **主动模式**：操作挂起，请求送交数据合规官，批准后才给临时令牌

官方强调：日志系统不仅记录「谁」和「访问了什么」，还记录「为什么」——这样安全团队才能跑异常检测（凌晨两点访问 500 个名人护照，理由栏是无意义字符 → 立即告警）。

### Object / Property Security Policies（2026-04-23 GA，2026-06-30 测试能力 GA）
- 在对象类型上直接配置权限，**独立于底层数据源权限**
- 组合 = **单元格级安全**：对象安全策略（行级）+ 属性安全策略（列级）
- **主键属性不能成为任何属性安全策略的成员**；一个非主键属性最多属于一个属性安全策略
- Granular policy 的比较权重上限：对象 + 属性两个策略合计必须低于 10,000
- 默认**继承**数据源的全部强制控制（标记、组织、分类），可新增也可移除已不需要的
- 支持测试：可选一个用户，测他能看到这个对象的哪些属性
  - 限制：不能测试派生属性的可见性（依赖源对象的可见性）
- **推荐从 Restricted Views 迁移到 object security policies**：统一单元格级安全、策略近乎即时更新、支持流式与分支
- **物化的坑**：对象安全策略也决定物化数据的权限，取最严格者；添加或移除标记后，标记只反映在该标记存在期间提交的事务——**历史事务需要额外手工打标记**
- 下载权限检查位置取决于对象类型存放在哪：存放在 project 中检查对象类型；用本体角色或数据源派生权限则检查底层数据源

### 数据保护与治理的联动
- **Cipher（功能性加密）**：三段式结构 Cipher Channel / Cipher License / Cipher Value；支持同一行内不同字段不同密级；连图像都能做可逆像素扰乱
- **stop_propagating**：可中断标记的遗传，但需要「移除标记」特权 + 分支保护 + **除作者外第二人审批**（双人控制）
- **受限视图 RV**：行级安全，如果 RV 过滤掉某行，对应对象在本体图谱中对该用户**不存在**
- **图谱中的权限传播**：链接可见性通常依赖两端对象的可见性——无权看机密文件时，是否能看到它的作者？这类防推断是治理的隐性难点

### 智能体时代的治理新增内容（Palantir 官方博客）
- Granular policies 可附着在整个本体上，同时约束**智能体与人类**对敏感信息的访问
- 策略在**运行时动态计算**，可组合数据层的行列限制、用户组属性（含 SSO 流过来的）、沿管道传播的安全标记
- **工具调用走与记忆相同的安全架构**：任何工具调用都依赖于本体中底层对象、属性、链接的访问权
- 工具可含**运行时校验**，依赖 granular submission criteria
- **出口策略（egress policies）**：管理到外部数据源、Webhook、API 端点的所有出站连接；任何导出到外部系统的数据都必须显式配置标记，定义可传输的数据类型
- **溯源安全（provenance-based security）**：构建尊重数据源强制控制的工具，在运行时生效；随简单函数嵌套进复杂工具仍可扩展
- **日志本身受治理**：AIP 让管理员控制日志在特定项目、工作流、智能体上如何被访问；数据标记等主动安全原语治理日志访问，与治理底层数据、逻辑、动作原语一致

### 其他官方机制
- **Data Catalog**：集合与文件的组织方式；集合按主题、受众、用途；任何人可看集合及其描述，但只能访问共享给他的精选文件；紫色对勾徽章标识
- **Data Health**：两个功能区——Monitoring views（范围型监控规则，随资源增加自动扩展）/ Health checks（单资源精细校验，含内容与 schema）；告警可走平台内通知、邮件摘要、PagerDuty / Slack / 任意 REST 端点
- **Linter**：分析登记状态识别反模式，给优化建议，可分配给用户并引导修复，定期复核影响
- **Metadata 四要求**（Palantir 博客）：Comprehensive Capture / Real-time Updates / Accessible for Review / Dynamic Trend Analysis

## 四、公网数据治理理论（引用依据）

- DAMA-DMBOK 六大知识域：数据治理、数据架构、数据质量、元数据管理、主数据管理、数据生命周期管理
- COBIT 2019 对治理的五大活动：确保治理框架有效、角色与责任清晰、治理机制融入流程、评估与报告、纠正与纠偏
- DCAM 数据管理能力成熟度模型：Data Governance 能力域（组织、流程、架构、指标、人员、技术）
- 数据契约（Data Contract）：生产者/消费者责任划分，字段级 SLA、兼容性规则、废弃流程
- 隐私工程七宗罪：数据收集超范围、目的漂移、留存过久、缺少删除、缺乏透明度、不安全共享、未做访问控制
- 元数据三类型：技术元数据、业务元数据、治理元数据（处理规则、血缘、质量、权限）
- 治理成熟度五级：L0 无意识 → L1 被动响应 → L2 主动管理 → L3 量化度量 → L4 优化自治
